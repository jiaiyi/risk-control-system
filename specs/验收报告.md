## 七、遗留问题

### 7.1 ❌ P0 · 案件详情拿不到冲突原因（AC-06 后半段）

- **现象**：`app/engine/decision.py::_build_case` 写入 `risk_case.risk_detail` 的 JSON 只含
  `final_score / score_breakdown / graylist_hit / rule_results`，**没有 `conflict` 键**；
  而 `app/service/case_service.py:324` 读的是 `risk_detail["conflict"]["detail"]`
  → `case_detail.conflict_detail` **恒为 `None`**。
- **影响**：黑白名单冲突案件能被筛出来（`conflict_flag=1` 正常），但详情页看不到冲突原因与命中名单，
  审核员无法据此判断。
- **验证**：`tests/test_event_pipeline.py::test_conflict_case_detail_shows_reason`（当前 `xfail`）
- **建议**：`_build_case` 增加 `conflict` 字段（或由 `event.process_event` 的冲突分支把
  `verdict.describe()` 与命中名单补写进案件 `risk_detail`）。

### 7.2 ❌ P0 · 案件详情不展示关联账号（AC-39 尾句 / P-10）

- **现象**：`case_service.case_detail` 返回值里 `"related_entities": []` —— **硬编码空列表**，
  注释写着「T-14 图谱接入」。
- **影响**：AC-39 要求的「案件详情关联图谱展示该地址下的其他账号」拿不到数据；
  审核员需手动去图谱页查询。
- **注意**：T-14 图谱服务**已完成**（`app/service/graph_service.py` 可用，AC-29 已通过），
  只是没接进案件详情 —— 属于集成遗漏，不是能力缺失。
- **验证**：`tests/test_case_service.py::test_case_detail_includes_related_entities`（当前 `xfail`）
- **建议**：按案件的 `event_type` + `source_id` 反查主体，调 `graph_service.query_graph()` 填充。

### 7.3 ⚠️ P1 · 规范与实现的口径不一致（需修订文档，不需改代码）

| 项 | 规范原文 | 实现 | 建议 |

| AC-08 | 「恰好 **37** 条记录（用户 14 / 订单 8 / 地址 3 / 登录 6 / 领券 6）」 | **43** 条（用户14/订单8/地址4/登录4/领券6/设备2/IP2/商品2/手机号1） | 修订 AC-08 为 43 项 —— 37 项是 G-14/G-15/G-19 补特征之前的旧口径 |
| AC-34 | 「8 条成功入库，2 条标红，不阻断其余记录」 | 任一行有错则**整批不入库**（SPEC Q9） | 二者不可兼得：要么修订 AC 采 Q9，要么改实现做部分入库。**当前实现与 Q9 自洽**，建议修订 AC |
| AC-39 | 「对其中一账号发起售后检查 → 命中 A001 / A002」 | A001 适用「下单」、A002 适用「售后申请」，需**两次检查** | 拆成两句话说清适用事件类型 |

### 7.4 ✅ 本次验收修复的缺陷

| # | 缺陷 | 位置 | 说明 |
|---|------|------|------|
| 1 | SQL 脚本硬编码库名 | `sql/init_risk_tables.sql:16`、`sql/init_risk_data.sql:16` | 两处 `USE ecs;` 写死库名。`init_db.py` 本就通过命令行参数指定库，`USE` 多余且**有害**：mysql 客户端执行 `USE` 时静默切库，表会建到错误的库且不报错。本轮建测试库时踩中（9 张风控表被建到主库 `ecs`，因 `CREATE TABLE IF NOT EXISTS` 才未造成损失）。已删除两行 |

### 7.5 ⚠️ P2 · 特征利用率：43 个特征中 8 个未被任何规则引用

自动统计（提取 41 条规则条件里的 `field`，与特征清单求差）：

```
特征总数 43 | 被规则引用 35 | 未被引用 8
未被引用：coupon_use_rate / order_discount_amount / order_item_count /
         order_sku_count / phone_refund_rate_24h / user_max_order_amount /
         user_postsale_count / user_refund_count
```

- **定性**：这些特征并非无用 —— 它们照常写入 `risk_feature` 快照，作为**证据链上下文**
  供人工审核查看（这本身是 PRD 要求的可解释性设计）。
- **但 G-19 明确要求补的 `phone_refund_rate_24h` 确实没有配套规则**，
  即「跨账号手机号退款聚集」只做了特征、没形成判定闭环。建议后续补一条规则（如
  `phone_refund_rate_24h >= 0.5 且退款笔数 ≥ 2`）以闭合该 Gap。

### 7.6 ⚠️ P2 · 场景数据的时间窗判据不足（已在测试侧绕过）

`scripts/_smoke.py::ensure_scenario_data` 的新鲜度判据只看 L001（「1002 近 1 小时失败登录 ≥5」），
而 C001/C002 依赖的是「1003/1006 近 1 小时领券次数」，后者更早滑出窗口 ——
于是会出现「判据说新鲜、领券场景却已失效」的**假回归**（本轮实际踩到：单跑通过、隔一段时间跑失败）。

- 测试侧已修：`tests/conftest.py` 改为**无条件**重建场景数据，不再依赖单一判据。
- **脚本侧仍建议修**：把判据扩展为多场景联合检查，或直接每次都重建。
